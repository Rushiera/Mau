> 版本：v1.0 | 2026-08-04 | G1 工程治理

---

## 一、分支策略

**主干开发（Trunk-Based Development）。**

| 分支 | 用途 | 规则 |
|:--|:--|:--|
| `master` | 唯一真相源 | 始终可编译、可运行门禁 |
| `feature/*` | 新功能/修复 | 从 master 切出，合并回 master |

- 小改动（<200 行）直接在 master 提交
- 中大型改动（≥200 行或跨多项目）走 `feature/` 分支，合并前跑完整门禁
- 不设 `develop`、`release` 等长驻分支——项目规模不需要

---

## 二、提交粒度

**一个提交 = 一个可独立理解的最小变更单元。**

| 规则 | 说明 |
|:--|:--|
| 原子性 | 一个提交只做一件事——改一个功能/修一个 bug/重构一个模块 |
| 可编译 | 每次提交后 `dotnet build Mau.sln` 零错误 |
| 门禁不倒退 | 不提交已知会破坏门禁的代码 |
| 禁止批量提交 | 不把"攒了一周的杂项"塞进一个 commit |

**提交信息格式：**

```
<阶段/范围>: <一句话摘要>

<可选详细说明——为什么这么做，不是什么>
```

示例：
```
P3.7: 补全通道类型静态验证——六通道参数匹配+死锁检测

翻译器 MauValidator.cs 新增 ChannelParamCheck 方法，
覆盖直连/inbox/工单/命令/快照/跨进程六种通道。
```

## 三、标签规则

**版本号采用 `v<主>.<次>.<修>`：**

| 段 | 触发条件 |
|:--|:--|
| 主版本 | 架构变更——接口断裂、不兼容升级 |
| 次版本 | 新功能——新增单元/积木/验证规则 |
| 修订版 | 修复——bug 修复/文档更新/重构（行为不变） |

**标签命令：**
```bash
git tag -a v0.1.0 -m "P3 第一期：翻译器原型最小闭环"
git push origin v0.1.0
```

当前版本：`v0.1.0`（P3 第一期完成）。

## 四、黄金文件与生成物纳入策略

### 纳入 Git 的生成物

| 路径 | 内容 | 纳入理由 |
|:--|:--|:--|
| `Mau.Snapshots/expected/*.cs` | 预期生成物 | **确定性校验基准**——翻译器输出必须逐字节匹配 |
| `Mau.Snapshots/cases/*.mau` | 测试语料 | 门禁输入——语料即测试用例 |

### 不纳入 Git 的生成物

| 路径 | 内容 | 不纳入理由 |
|:--|:--|:--|
| `Mau.Snapshots/generated-run/` | 实际运行产物 | 可从语料重建——`mau gen` 随时再生 |
| `bin/` `obj/` | 编译中间产物 | .gitignore 已排除 |
| `artifacts/` | 打包产物 | 已排除 |

### 黄金文件检查清单

每次提交涉及翻译器修改时：
1. 跑 `mau test`（门禁全量）
2. 如果黄金文件对比失败 → 确认差异是预期行为 → 更新 `expected/` → 一并提交
3. 黄金文件变更必须在提交信息中说明原因
