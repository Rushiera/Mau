# 04 · 管家与馆长

> 两个「管理型」身份——一个管运行中的宿主与猫（Majordomo），一个管知识与文档（Akasha）。

## Majordomo — 宿主管家

**定位：** 宿主与多猫的管理面——猫生命周期 / 配置 / 部署重启。默认会话（主控猫）持有；特权工具仅默认会话可见可调。

| 能力 | 说明 |
|:--|:--|
| **猫生命周期** | 启动 / 暂停 / 继续 / 停止单只猫；新建 / 删除猫；全猫状态一览 |
| **配置管理** | 全局配置 + 每猫配置（显示名 / 人格 / 模型端点 / 工具面 / 受控根）读写 |
| **部署与重启** | 宿主重启三档——`restart-full`（全链）/ `restart-incr`（纯搬运）/ `restart-host`（原地） |
| **全猫统计** | 各猫运行状态、端口、四相环、前文长度、最近活跃、轮次、消息数 |

**重启是特权动作：** 只经 Majordomo 会话的特权工具触发，不由其他路径发起（见 02 红线 5）。三档按需选——日常改动优先「仓库内 prepare + `restart-incr`」，版本发布 / 全链保底才用 `restart-full`。

**为什么要有管理面：** 宿主常驻、数据本机——停机部署会打断所有猫。分层设计让「改动生效」尽量走热重载（零停机），只有不可热替换的宿主程序集才走重启链；重启前置零停机、验证不过保持原版本运行。

## Akasha — 知识馆长

**定位：** 文档治理与知识固化——收工 / 蒸馏 / 审查。不生产知识，承载并保养已结晶的知识。

| 能力 | 说明 |
|:--|:--|
| **收工** | 一段工作收尾——更新项目档案 / 待办 / 变更日志，归档判例与灵感，清理临时区 |
| **蒸馏** | 从真实判例里析出可复用的规则，修正「唯一态」文档——不留痕 |
| **审查** | 关系扫描 + 路由一致性核查——找死链、孤儿文件、命名漂移、覆盖遗漏 |
| **Project 文档维护** | 建档 / 更新 / 归档；设计与兑现分离（设计文档不带进度，兑现明细归 `_log`） |

**收工三律：** ① 触发即拉取收工包；② 报告是**终态断言**（零疑问句）；③ 未决事项归文件（待办 / 判例），不抛给人等回应。

**为什么对使用者有用：** 任何长期维护的文档项目都会积累「历史与现状混写」的熵——收工 / 蒸馏机制是对抗这种熵的固定流程：把「做过什么」与「还要做什么」分流到不同承载面，让后来人一眼看清现状。

## 权限声明

两个身份在各自域内持有**受豁免的判断权**——为效率主动推进一步、直接选定最优方案，做完再汇报。这是设计选择：结构维护靠判断，不靠逐条请示。该豁免须显式声明方生效（见 02「例外与授权」）。

## 什么时候会用到

| 你想做的事 | 找谁 |
|:--|:--|
| 加 / 删一只猫、改某猫配置 | Majordomo（管理面板 / 指令） |
| 重启宿主、部署新版本 | Majordomo（特权链） |
| 一段工作收尾、更新项目文档 | Akasha（收工） |
| 把重复踩的坑固化成规则 | Akasha（蒸馏） |
| 文档死链 / 孤儿文件排查 | Akasha（审查） |
